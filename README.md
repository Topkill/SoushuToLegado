# 搜书大师转阅读工具

<strong>使用前第一步：**备份搜书大师的数据和阅读的数据，阅读的数据也要备份一下**</strong>

脚本负责把**搜书大师**的本地备份（`ssds.backup` / `.zip`）转成 **Legado（阅读）** 能导入的书架备份。

目标很简单：尽量把“搜书大师的书架、书架上的书、阅读进度、搜索历史”迁过去。  
**不是**把搜书大师完整搬家，也**不能**保证导入后马上继续在线看同一本书。

---

## 它能做什么

可以转换**搜书大师**的这些内容：

### 1. 书架

搜书大师里的书架，会转成 Legado 的**自定义分组**。

### 2. 书架上的书
- **非本地书**，或者说网文书，网络书，用书源搜索到的书（`.wbpub`）
- **本地书**（如 txt）

会**尽量**带上：
- 书名、作者
- 简介、封面
- 书籍地址
- 分组
- 章节进度
- 当前章节名
- 最近阅读相关时间

会转换单书阅读时长到 Legado 阅读记录：

- 当前书累计阅读时长（`readTime`）
- 近似最近阅读时间（`lastRead`，不够精确）

不转换：

- 阅读速度
- 按天阅读日期明细
- 累计阅读字数


### 3. 阅读进度
包括：
- 读到第几章
- 章内位置
- 当前章节标题
- 最近阅读顺序

关于“最近阅读”：
- 搜书大师主要靠 `history.txt` 记录最近打开顺序
- 脚本严格按这个顺序生成 `durChapterTime`（顺序不变）
- 有 `statistics.dates` 的书尽量锚到真实阅读日；没有的书贴在上一本后面（`上一本时间 - 1`）
- 这样在 Legado 里选 **默认（即按阅读时间）** 排序时，**每个书架内部顺序**会尽量和搜书大师一致

### 4. 搜索历史
搜书大师里搜过的书名关键词，会转成 Legado 的搜索历史。

## 怎么用

### 环境
- Windows / macOS / Linux 都行
- 需要 Python 3.10+（一般 3.11 也行）
- 不需要额外安装第三方库

### 基本命令

```bash
python convert_bookshelf_backup.py "你的ssds.backup"
```

默认会在同目录生成：

```text
backup-converted.zip
```

### 指定输出文件

```bash
python convert_bookshelf_backup.py "ssds.backup" -o "legado-bookshelf.zip"
```

### 额外生成转换报告

```bash
python convert_bookshelf_backup.py "ssds.backup" -o "legado-bookshelf.zip" --report "report.md"
```

### 导入 Legado
1. 用本脚本生成 `backup-converted.zip`
2. 打开 Legado
3. 选择恢复/导入备份
4. 导入刚生成的 zip

导入后建议：
- 排序选 **默认（即按阅读时间）**，才能看到和搜书大师接近的最近阅读顺序
- 非本地书如果打不开正文，去重新搜索/换源绑定
- 本地书如果打不开正文，是本地书的文件没有迁移，自己重新导入一下

## 转换后会有哪些文件

脚本输出的是一个精简的 Legado 备份，通常包含：

```text
bookshelf.json      # 书架书籍
bookGroup.json      # 分组
searchHistory.json  # 搜索历史
readRecord.json     # 阅读记录（累计时长）
```

它**不会**生成完整 Legado 备份里的所有东西，例如书源、主题、替换规则、TTS 等。

---

## 重要限制（请先看）

### 1. 这是“书架迁移”，不是“完整搬家”
能迁的是书架状态，不是搜书大师 App 的全部数据。

### 2. 不迁移书源
两边书源体系不一样。  
脚本**不会**把搜书大师的书源转成 Legado 书源。

结果是：
- 书出现在原来的书架上
- 进度、分组、书名等信息通常在
- 但不保证点开后还能按原来的书源继续在线更新/阅读
- 需要的话，请在 Legado 里重新搜书、换源

### 3. 不迁移替换规则、主题、阅读排版
这些都不转：
- 净化/替换规则
- 主题皮肤
- 字体、边距、翻页方式
- 书架布局（列表 / 网格）

原因：两边配置模型差太多；另外 Legado 的书架布局是全局的，搜书大师支持“每个书架不同布局”，没法原样对应。

### 4. 最近更新排序不能准确还原
搜书大师有“最近更新排序”，但它主要按“当前有没有更新”这类状态排，  
**不是**稳定保存的“每本书最近更新时间”。

备份里通常没有可靠的：
```text
每本书的最近更新时间戳
```

所以脚本**没法**让 Legado 的“按更新时间”和搜书大师完全一致。

### 5. 搜书大师默认“按加入时间”排序，Legado 没有同款
搜书大师默认大致是按加入书架时间排。  
Legado 默认是按阅读时间排，没有单独的“加入时间排序”。

脚本会把加入时间写到相关时间字段里做近似，但：
- **不能 100% 当成搜书大师的加入时间排序**
- 一旦某本书读过，阅读时间就会和加入时间分开

### 6. 已删除的书、历史残留不会乱进书架
搜书大师的 `history.txt` 里可能还有：
- 已删除的书
- 换源前的旧路径
- 打开过但没进书架的文件

脚本只会处理**当前还在书架上的书**。  
历史里有、书架上没有的，会自动忽略。

### 7. 历史里可能还有已删除的书
搜书大师的`history.txt` 不会随着删书自动打扫干净。

比如：
- 历史里还留着「我欲封天(提刀小生)」
- 但这本书其实已经删了
- 书架上现在是另一本「我欲封天(耳根)」

脚本只会认**当前还在书架上的书**。  
历史里已删除、或同名但路径/作者不同的旧记录，都不会拿来给当前书对进度。

### 8. 本地书通常只有元数据，没有原文件内容
如果备份里没有真正的 txt/epub 正文文件，  
Legado 里可能只能看到书名等信息，打不开正文。

### 9. 书签、笔记
搜书大师数据库里有相关表，当前脚本暂时**不转换**书签/笔记。

阅读时长会尽量转换到 `readRecord.json`：
- `usedTime` → `readTime`（较准确）
- `lastRead`：
  - 全局最近一本可用 `lastFile`/`lastReadTime`（较准）
  - 其他书用 `statistics.dates` 最后一天（只有日期）
  - 再没有才用加入时间
  - **不用** history 递减时间戳
- 阅读速度、按天明细、累计字数不转换

### 10. 不能保证“导入就能接着在线看”
最稳的预期是：

> 书架在、书在、进度大致在。  
> 在线阅读/更新能力需要你在 Legado 里重新绑定书源。

## 可以转换 / 不能转换 一览

### 可以转换

- 书架

- 书架书籍列表
- 书名、作者、简介、封面（有数据时）
- 当前章节进度
- 当前章节名（非本地书）
- 最近阅读顺序（尽量对齐）
- 搜索历史
- 单书累计阅读时长（阅读记录）

### 不能转换 / 不保证
- 书源规则
- 在线继续阅读能力
- 替换净化规则
- 主题 / 字体 / 排版
- 书架布局
- 精确的“最近更新时间排序”
- 精确的“加入时间排序”
- 书签 / 笔记
- 阅读速度 / 按天阅读日期 / 累计阅读字数
- 精确的 lastRead（只能近似）
- 正文缓存 / 本地书原文件（备份里没有就没有）
- Cookie / 登录态 / TTS 等

## 导入后怎么最接近搜书大师

1. 先导入脚本生成的备份
2. Legado 排序选**默认**（即**按阅读时间**）
3. 检查分组是否正确
4. 非本地书如无法更新/阅读，手动换源
5. 不要求布局、主题和搜书大师一模一样

如果你搜书大师里开的是“最近阅读排序”，这一套体验最接近。  
如果搜书大师里是“默认加入时间”或“最近更新”，只能近似，无法完全一致。

## 常见问题

### Q: 为什么书在，但点开不能读？
因为没迁书源，或者本地书原文件不在备份里。  
请在 Legado 重新搜书/换源，或自行补本地文件。

### Q: 为什么最近阅读顺序大体对，但有几本不对？
常见原因：
- 那本书不在 `history.txt`
- 历史里是旧路径，书架里是新路径
- 书已换源/重加过

### Q: 为什么没有书源？
当前版本明确不做书源迁移。两边书源不通用。

### Q: 会不会覆盖我现有 Legado 数据？
会覆盖，一定**先备份自己的 Legado**，再导入。

### Q: 支持很大的备份吗？
至少 100MB 左右的备份都没啥问题。  
脚本是按条目读取，不是一次把整个包全塞进内存；  
但如果单本的章节列表特别大，会更吃内存和更慢。

---

## 一句话总结

这个脚本适合：

> 想把搜书大师里的**书架、书籍、进度、搜索历史**迁到 Legado。

不适合指望：

> 原封不动继承书源、主题、布局、更新排序，并马上继续无缝在线看。

能迁的尽量迁了；不能迁的，主要卡在两边设计不同，不是单纯“少写几个字段”。
